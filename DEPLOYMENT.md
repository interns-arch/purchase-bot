# Deployment Guide

Production architecture:

```
Frontend (React + Vite)  ->  Vercel
Backend  (FastAPI)        ->  Render
Database (SQLAlchemy)     ->  SQLite locally, PostgreSQL in production
```

No business logic changed for deployment. The web app is a thin wrapper
around the existing `core/` package (matching engine, import services,
document processing) -- everything below is infrastructure/config only.

---

## 1. Backend deployment (Render)

This repo includes a Render Blueprint at `render.yaml` (repo root). From the
Render dashboard: **New +** -> **Blueprint**, point it at this repo, and
Render reads `render.yaml` and provisions the service.

What it configures:

- **Build:** `pip install -r backend/requirements.txt`
- **Start:** `uvicorn backend.app.main:app --host 0.0.0.0 --port $PORT`
  (no `--reload` -- that flag is dev-only)
- **Health check:** `GET /health` (also available at `GET /api/health`)
- **Runtime:** Python 3.13 (set via the `PYTHON_VERSION` env var, which is
  what Render's Python-buildpack reads -- no separate `runtime.txt`/`Procfile`
  needed since the Blueprint already declares the build/start commands)

After the first deploy, set these in the Render dashboard (they're marked
`sync: false` in `render.yaml`, meaning Render won't auto-generate them --
you fill them in):

| Variable | What to set it to |
|---|---|
| `DATABASE_URL` | Your Postgres connection string (Neon, Render Postgres, Supabase, etc.) |
| `CORS_ORIGINS` | Comma-separated list, e.g. `https://your-app.vercel.app,http://localhost:5173` |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | Optional one-time bootstrap -- see §4 |

`JWT_SECRET_KEY` is auto-generated by Render (`generateValue: true`) and kept
stable across deploys.

If you'd rather deploy manually (no Blueprint): create a **Web Service**,
set the same build/start commands above, and add the environment variables
from `backend/.env.example` yourself.

### Render free-tier caveat

The free plan has **no persistent disk** -- anything written to
`UPLOAD_DIR`/`TEMP_UPLOAD_DIR`/etc. is wiped on every redeploy or restart.
This only affects the *original* uploaded files kept for reference; all
imported data lives in Postgres and is unaffected. If you need the original
files to survive restarts, that's what "cloud storage can be added later"
(§5) is for.

## 2. Frontend deployment (Vercel)

From the Vercel dashboard: **Add New** -> **Project**, import this repo, set
**Root Directory** to `frontend/`. Vercel auto-detects Vite
(build command `npm run build`, output directory `dist`).

`frontend/vercel.json` configures SPA routing so refreshing any client-side
route (e.g. `/vendor-comparison`) doesn't 404:

```json
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}
```

### Environment variable

Set in the Vercel project's **Settings -> Environment Variables**:

```
VITE_API_BASE_URL=https://your-backend.onrender.com
```

Every API call goes through `frontend/src/api/client.js`, which reads
`import.meta.env.VITE_API_BASE_URL` -- no component ever hardcodes a URL.
Vite only exposes env vars prefixed `VITE_` to client code, and only bakes
them in at build time, so **changing this value requires a redeploy**
(Vercel does this automatically if you trigger one after editing the
variable).

---

## 3. How to change the backend URL

Change exactly one place: the `VITE_API_BASE_URL` environment variable in
the Vercel project (or `frontend/.env` for local dev). Nothing in the
frontend source references a URL directly.

## 4. Environment variables reference

Copy `backend/.env.example` to `backend/.env` for local dev (git-ignored --
never commit it). In production, set these in the Render dashboard instead.

| Variable | Purpose | Default |
|---|---|---|
| `DATABASE_URL` | Postgres connection string. Unset -> falls back to local SQLite (`database/app.db`) | *(unset)* |
| `JWT_SECRET_KEY` / `SECRET_KEY` | Signs JWTs. `SECRET_KEY` is accepted as a fallback alias | random per-restart if unset (dev only) |
| `ALGORITHM` | JWT signing algorithm | `HS256` |
| `JWT_EXPIRE_MINUTES` / `ACCESS_TOKEN_EXPIRE_MINUTES` | Access token lifetime, minutes. Second name is a fallback alias | `480` |
| `CORS_ORIGINS` | Comma-separated allowed origins -- **never `*` in production** | `http://localhost:5173,http://127.0.0.1:5173` |
| `UPLOAD_DIR` | Where successfully processed files land | `uploads/processed` |
| `TEMP_UPLOAD_DIR` | Where incoming files land before classification | `uploads/incoming` |
| `ARCHIVE_UPLOAD_DIR` | Reserved for a future retention job | `uploads/archive` |
| `FAILED_UPLOAD_DIR` | Failed / needs-review files | `uploads/failed` |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | One-time admin bootstrap -- only takes effect while zero user accounts exist | *(unset)* |
| `LOG_LEVEL` | Minimum log level | `INFO` |
| `WHATSAPP_ENABLED` | `true`/`false` -- see §6 | `false` |
| `WHATSAPP_GRAPH_API_VERSION` | Meta Graph API version | `v23.0` |
| `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_BUSINESS_ACCOUNT_ID`, `WHATSAPP_APP_ID`, `WHATSAPP_APP_SECRET` | Meta Business App credentials -- see §6 | *(unset)* |
| `WHATSAPP_WEBHOOK_VERIFY_TOKEN` / `WHATSAPP_VERIFY_TOKEN` | Webhook handshake token. Second name is a fallback alias | *(unset)* |

For the frontend, only one variable: `VITE_API_BASE_URL` (see §2).

`JWT_SECRET_KEY`/`JWT_EXPIRE_MINUTES` are this app's original names and are
what `render.yaml` already provisions; `SECRET_KEY`/`ACCESS_TOKEN_EXPIRE_MINUTES`
are accepted as fallback aliases so either naming convention works without
code changes.

## 5. Database: SQLite -> PostgreSQL

Nothing in the code needs to change. `core/db.py` picks the backend purely
from whether `DATABASE_URL` is set:

- **Unset** (default, local dev): SQLite file at `database/app.db`.
- **Set**: PostgreSQL, via `sqlalchemy` + `psycopg2-binary` (already in
  `backend/requirements.txt`). Both `postgres://` and `postgresql://`
  connection string forms are accepted and normalized internally.

To switch:

1. Provision a Postgres instance (Neon, Render Postgres, Supabase, RDS, etc.)
2. Set `DATABASE_URL` in `backend/.env` (local) or the Render dashboard (prod)
   to its connection string.
3. Restart the backend. Tables are created automatically on first connection
   (`Base.metadata.create_all`) -- no manual migration step for a fresh
   database.

Local development can keep using SQLite indefinitely; there's no dependency
on Postgres existing for the app to run.

## 6. Enabling WhatsApp later

The integration (`backend/app/integrations/whatsapp/`) is fully
environment-driven today. With `WHATSAPP_ENABLED=false` (the default), the
webhook route accepts requests but no-ops -- **no code changes are needed
to go live**, only configuration:

1. Create a Meta Business App + WhatsApp Business Account at
   https://developers.facebook.com/apps
2. Under the app's **WhatsApp -> API Setup**, note the phone number ID and
   WhatsApp Business Account ID; under **Settings -> Basic**, note the App
   ID and App Secret.
3. Set in `backend/.env` (or the Render dashboard):
   ```
   WHATSAPP_ENABLED=true
   WHATSAPP_ACCESS_TOKEN=<permanent system-user token, recommended over a short-lived one>
   WHATSAPP_PHONE_NUMBER_ID=<...>
   WHATSAPP_BUSINESS_ACCOUNT_ID=<...>
   WHATSAPP_APP_SECRET=<...>
   WHATSAPP_WEBHOOK_VERIFY_TOKEN=<any string you choose>
   ```
4. In the Meta App Dashboard's webhook configuration, point it at
   `https://<your-render-service>.onrender.com/api/whatsapp/webhook` and
   enter the same value you chose for `WHATSAPP_WEBHOOK_VERIFY_TOKEN`.
5. Redeploy (or just restart, since these are plain env vars).

`WHATSAPP_APP_SECRET` is required for webhook signature verification
(`X-Hub-Signature-256`); without it, incoming payloads are accepted
unsigned, which is fine for local testing but must be set before exposing
the webhook publicly.

## 7. CORS

`CORS_ORIGINS` is a comma-separated allowlist read by
`backend/app/core/config.py` and applied via FastAPI's `CORSMiddleware`.
Include both your local dev origin and your Vercel URL once you have it:

```
CORS_ORIGINS=http://localhost:5173,https://your-app.vercel.app
```

The backend logs a warning at startup if `CORS_ORIGINS` ever contains `*` --
don't use a wildcard in production.

## 8. Logging, error handling, and health checks

- **Logging:** every request is logged (`method path -> status (duration)`),
  along with startup, import status, document processing, and webhook events
  via the existing `core.logging_setup.get_logger`. Level is controlled by
  `LOG_LEVEL`.
- **Error handling:** expected errors (`HTTPException`, e.g. 404/400/401)
  already return clean JSON (`{"detail": "..."}"`) via FastAPI's defaults.
  A catch-all handler in `backend/app/main.py` covers anything unexpected:
  it logs the full exception server-side and returns a generic
  `{"detail": "Internal server error."}` (HTTP 500) to the client --
  stack traces are never exposed.
- **Health check:** `GET /health` (Render's `healthCheckPath`) and
  `GET /api/health` both return `{"status": "ok"}`.

## 9. Common deployment issues

- **CORS errors in the browser console:** `CORS_ORIGINS` on the backend
  doesn't include your Vercel URL, or you forgot to redeploy the backend
  after changing it. Env var changes require a restart to take effect.
- **Frontend calls `127.0.0.1:8000` in production:** `VITE_API_BASE_URL`
  wasn't set in Vercel before the last build (Vite bakes it in at build
  time, not runtime) -- set it, then trigger a redeploy.
- **Refreshing a route 404s on Vercel:** `frontend/vercel.json` is missing
  or wasn't picked up -- confirm it's committed and Vercel's Root Directory
  is set to `frontend/`.
- **Logins stop working after a Render redeploy:** `JWT_SECRET_KEY` wasn't
  set explicitly, so a new random one was generated at boot, invalidating
  every existing session. Set it explicitly (Render's Blueprint does this
  automatically via `generateValue: true`, but manual Web Service setups
  must set it themselves).
- **Uploaded files "disappear" after a Render redeploy:** expected on the
  free plan -- no persistent disk (see §1). The imported *data* is safe in
  Postgres; only the original uploaded files are affected.
- **Admin bootstrap doesn't create a user:** `ADMIN_USERNAME`/`ADMIN_PASSWORD`
  only take effect while **zero** user accounts exist. If one already exists,
  use `python -m backend.scripts.create_admin --username admin --reset`
  instead.
- **502s / cold-start timeouts on Render's free plan:** free services spin
  down after inactivity and take a few seconds to wake on the next request --
  not an error, just the free tier's cold-start behavior.
- **`ModuleNotFoundError: No module named 'backend'`:** the backend must be
  run from the repository root (`uvicorn backend.app.main:app`), not from
  inside `backend/` -- this is already how `render.yaml`'s `startCommand`
  invokes it.
